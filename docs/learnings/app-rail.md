# Learnings: the app rail

- **Bigger rail items cost apps above the fold.** Going from 20px to 30px icons (and a 68px rail) means a 1280x800 window shows about 8 of 15 apps instead of 12. The scrollbar is hidden, so the list now fades out at the bottom (`data-more` on `rail-apps`) while more apps sit below. Any future size change should check the fold at 800px tall.
- **Bounding boxes are not whole pixels.** Playwright returned 67.99999 for a 4.25rem rail and 30.000001 for a 30px icon. Use `toBeCloseTo` or round before comparing.
- **The cloud sandbox's Chromium doesn't match this repo's Playwright.** Run e2e with `PLAYWRIGHT_CHROMIUM=/opt/pw-browsers/chromium` (playwright.config.ts reads it).
- **To look at the demo locally,** `pnpm --filter @hearth/web build:demo` writes `site/public/demo`; serve it with any static server and open `/` (deep links 404 without the site worker's fallback).
- **`e2e/checkins.spec.ts` takes about two minutes** and failed once on a full run while other builds shared the CPU, then passed three times alone. If it fails again, look at its run time before blaming your change.
- **Pinning changed what e2e can click.** Specs that clicked an unpinned app on the rail (Dictate, Clips, Whiteboard) now go through the `openApp(page, id)` fixture, which opens the launcher. Use it for any app that isn't one of the default pins.
- **Module-level stores leak between unit tests.** `apps/pins.ts` keeps the pins in a module variable; `src/test/setup.ts` calls `forgetPins()` after each test, the way the tests already clear localStorage. A new store like it needs the same line.
- **jsdom has no `setPointerCapture` or `elementFromPoint`.** userEvent's click fires pointerdown, so a drag handler that captures the pointer must call it optionally, or every click in edit mode throws.
- **Fewer rail items moved the fold test.** With five pins the list only overflows on a very short window; the fade test now uses 380px tall.
- **Two checkouts running e2e on one Mac share a server.** `reuseExistingServer` is on outside CI, so a second run on port 3999 silently tests the first checkout's build (old icons, no launcher). Run with `E2E_PORT=4099 E2E_SETUP_PORT=4098` when another thread may be testing, and don't run `build:demo` while e2e runs: it rewrites `apps/web/dist` with the mock build.
- **A ResizeObserver on a scrolling list misses new content.** The fade hint (`data-more`) watched only the list's own size, so pinning a tenth app grew `scrollHeight` without telling anyone and the fade never appeared until a scroll or a window resize. A `MutationObserver` on the list's children now re-checks it. Any "more below" hint needs both.
- **Lifting a cap is mostly tests and words.** The six-pin limit lived in four places: the web store's `slice`, the launcher's disabled tiles and help line, the server's zod `.max`, and the help center (getting started, plus its copy in the help home's search text). Grep for the number in words too ("six").
- **The phone bar has its own list.** `pins.ts` now builds both stores from one `pinList` factory (rail: `/api/pins`, phone: `/api/phone-pins`), and `forgetPins()` clears both. A third per-member list of app ids should be one more `pinList` call, not a copy of the store.
- **Drag-to-reorder lives in `usePinDrag`.** The launcher and the Apps sheet share it; jsdom has no `elementFromPoint`, so unit tests stub `document.elementFromPoint` to the target item and fire pointer events, then a click (the click after a drag must not count as a tap).
- **Anything that asked "is this app on the phone bar?" read `onPhoneBar` from the manifests.** That field is gone; the Apps tab now gets the set of ids on the bar as a prop. Grep for the old field name if an older branch merges in.
- **Six tabs fit a 375px phone.** At 62px each, labels up to "Check-ins" and "Briefcast" fit at 10px; e2e mobile checks no label is clipped with five apps plus Apps.
- **A row that grows inside a `Menu` pushed it off the screen.** `Menu` placed itself once, from its first size. The account menu's Music row opens the controls under itself, so `Menu` now places itself again on every resize (a `ResizeObserver`) and scrolls inside when it is taller than the window. Any new menu row that expands gets this for free.
- **A hidden file field outside a menu closes the menu in unit tests, not in browsers.** `userEvent.upload` clicks the field first, which `Menu` takes for a click outside. The real file dialog opens with no pointer event, so tests fire `change` on the field instead (`pick()` in `profile/photo.test.tsx`), and the e2e spec uses the real file chooser to prove the menu stays open.
- **Keep the file field outside the menu.** It is rendered beside the account button, so a pick still lands if the menu was closed while the dialog was open.
- **Removing a rail button is mostly other people's tests.** `settings-link`, `music-button` and `feedback-link` were clicked by seven e2e specs and five unit tests that had nothing to do with the rail. Grep the test ids across `e2e/` and `apps/web/src` before removing a button, and the help center (and its lowercase copy in the help home's search text) for the words "gear" and "music note".
- **The server has no image library, and doesn't need one for avatars.** The browser crops and shrinks with `createImageBitmap` and a canvas; the server only reads the first bytes to decide the type. jsdom has neither, so unit tests stub `createImageBitmap`, `getContext` and `toBlob` and assert the crop rectangle.
- **`title` on a rail entry doubles up with a custom tip.** The native tooltip appears about a second after ours. The entries keep `aria-label` and drop `title`.
- **`--rail-width` is the one number.** The launcher, the side panel and the update note all read it, so widening the rail is a single attribute on `<html>`; nothing else needed to know.
- **`FeedbackScreenshots.test.tsx` S7 is flaky on main** (3 of 5 runs failed on unchanged main, Nov 19: the sent state is awaited for one second after a multipart send). If it fails on your branch, run it alone before blaming your change.
